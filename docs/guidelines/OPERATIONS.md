# 온담 운영·배포 가이드

> 작성 배경: 문서 세트에 인프라·배포·장애 대응이 전혀 없었다. PRD 4장에 스택 나열은 있으나 **"어떻게 배포하고 무엇이 터질 때 무엇을 보는가"**가 없다.
> **주의**: 아래 인프라는 PRD에 기록된 *계획*이다. 실제 구축 여부는 확인되지 않았으므로, 각 항목에 `[미확인]` 표시가 있으면 먼저 실물을 확인하고 이 문서를 갱신할 것.

## 1. 구성 요소

| 구성 | PRD 계획 | 상태 |
|---|---|---|
| 앱 서버 | AWS EC2 + Docker | [미확인] |
| DB | MySQL 8.4 (InnoDB, utf8mb4) | 스키마 파일 존재, 인스턴스 [미확인] |
| 캐시·큐 | Redis (BullMQ) | [미확인] |
| 파일 | AWS S3 (+ KMS 암호화) | 코드 연동 완료, 버킷 [미확인] |
| CDN | CloudFront | [미확인] |
| CI/CD | GitHub Actions | [미확인] |
| DNS | Route 53 | [미확인] |
| 결제 | 토스페이먼츠 | 키 발급 [미확인] |
| AI | D-ID(립싱크), ElevenLabs(음성), Gemini(사진) | 계정 [미확인] |

**프로세스 구성**: 앱 서버와 **워커가 분리 실행**된다(`npm run workers`). 워커 프로세스(`jobs/index.js`)에는 Socket.IO 인스턴스가 없어 실시간 진행률 emit이 동작하지 않는다 - 프론트는 폴링으로 처리 중. 실시간이 필요해지면 Redis adapter 도입 필요.

## 2. 환경변수 (39개)

`backend/.env.example`이 정본이다. 신규 변수를 추가하면 반드시 `.env.example`과 `config/validateEnv.js`에 함께 등록한다(누락으로 업로드가 전부 실패한 전례가 있다).

### 그룹별 요점
- **서버**: `PORT`, `NODE_ENV`, `TZ=Asia/Seoul`, **`TRUST_PROXY_HOPS`**
  - `TRUST_PROXY_HOPS`는 기본 0(프록시 없음). **프록시(nginx/ALB) 뒤에 배포하면 반드시 홉 수를 설정**해야 한다. 설정하지 않으면 rate limit이 전 사용자 단일 버킷으로 동작해 사이트 전체가 잠길 수 있다. `true`로 두면 헤더 위조로 우회 가능하니 숫자로 지정한다.
- **DB/Redis**: `DB_*`, `REDIS_*`
- **인증**: `JWT_SECRET`, `JWT_REFRESH_SECRET`, 만료 설정
- **AWS**: `AWS_REGION`, 액세스 키, `S3_BUCKET`, `KMS_KEY_ID`
- **결제**: `TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`, `TOSS_WEBHOOK_SECRET`, `TOSS_CONFIRM_TIMEOUT_MS`, `PAYMENT_MOCK`
- **정기결제**: `BILLING_SCAN_CRON`, `BILLING_MAX_RETRIES`, `BILLING_GRACE_DAYS`, `BILLING_RETRY_INTERVAL_DAYS`, `BILLING_PENDING_STALE_MINUTES`, `TOSS_BILLING_TIMEOUT_MS`
- **AI**: `GEMINI_API_KEY`, `ELEVENLABS_API_KEY`, `LIPSYNC_PROVIDER`, `DID_API_KEY`(+ 예비 `SYNC_API_KEY`, `FAL_API_KEY`)
- **프론트**: `CLIENT_URL`

### 운영 원칙
- `.env`는 절대 커밋하지 않는다. 시크릿은 배포 환경의 비밀 관리 수단으로 주입한다.
- **`PAYMENT_MOCK`이 프로덕션에서 true면 안 된다.** 배포 체크리스트에 포함.
- 키 로테이션 대상: JWT 시크릿, AWS 키, 토스 시크릿, AI 벤더 키. 유출 시 즉시 교체 + 영향 범위 점검.

## 3. 배포 절차

### 3-1. 사전 조건
1. 마이그레이션이 **코드 배포보다 먼저** 적용돼야 한다. 현재 대기 중인 2건은 순서가 있다:
   `2026-08-21-schema-drift-fix` → `2026-08-21b-memorial-visibility-and-consent`
   순서를 어기거나 일부만 적용하면 회원가입·추모관이 동작하지 않는다.
2. 마이그레이션 실행 전 **DB 백업 필수**. 롤백용 DOWN 스크립트가 함께 있으나, ENUM 값 제거는 무손실 롤백이 불가능하므로 백업이 유일한 안전망이다.

### 3-2. 순서
```
1) DB 백업
2) 마이그레이션 UP 적용 (a → b 순서)
3) 앱 서버 배포 (무중단이 아니면 짧은 점검 공지)
4) 워커 프로세스 재시작
5) 기동 검증 (아래 3-3)
6) 스모크 테스트 (E2E 필수 시나리오)
```

### 3-3. 기동 직후 반드시 확인할 것
- [ ] 서버 기동 로그에 에러 없음
- [ ] **정기결제 스케줄러 등록 로그** - `[billingQueue] scan-due 스케줄러 등록 확인됨 - pattern=... next=...`가 실제로 찍히는가. 이 로그가 없으면 자동결제가 조용히 죽은 것이다(과거 실제로 발생)
- [ ] 워커 프로세스가 큐를 잡고 있는가
- [ ] `/api/subscriptions/plans` 등 비인증 엔드포인트 200
- [ ] 프론트 로드 → 비로그인 상태로 공개 페이지 접근 가능
- [ ] `NODE_ENV=production`에서 500 에러에 원문 메시지가 노출되지 않는가

### 3-4. 롤백
- 앱: 이전 이미지로 되돌린다.
- DB: **마이그레이션 롤백은 신중히.** 새 컬럼에 이미 데이터가 쌓였으면 DOWN이 데이터를 지운다. README의 사전 확인 쿼리를 먼저 돌린다.
- 앱만 롤백하고 스키마는 두는 편이 대체로 안전하다(추가된 컬럼·ENUM 값은 구버전 코드가 무시한다).

## 4. 모니터링 (무엇을 보는가)

현재 모니터링 체계가 없다. 최소한 아래는 갖춰야 한다.

### 4-1. 반드시 알림 받아야 할 것
| 신호 | 왜 | 임계 |
|---|---|---|
| **AI 작업 최종 실패율** | 실패는 자동 환불로 이어진다. 원가 누수 + CS | 급증 시 즉시 |
| **결제 실패율 / 불확정 건수** | 자금 직결. 불확정(pending 잔존)은 사람이 확인해야 한다 | 1건이라도 |
| **정기결제 스캔 미발화** | 조용히 안 도는 것이 이 시스템의 알려진 실패 모드 | 예정 시각에 로그 없으면 |
| **DB 커넥션 풀 고갈** | `connectionLimit: 10`. 외부 API 지연이 겹치면 전체 API 정지 | 사용률 80%+ |
| **큐 적체** | 워커가 죽으면 주문이 쌓이고 사용자는 기다린다 | 대기 건수 급증 |
| **5xx 급증** | | |
| **S3/KMS 오류** | 업로드·암호화 실패는 곧 기능 정지 | 1건이라도 |

### 4-2. 로그에서 봐야 할 것
- `audit_logs`: 관리자 행위(특히 사후 공개 승인) 전량
- `ai_jobs`: 상태 전이와 실패 사유
- `subscription_payment_logs`: pending 잔존 건(불확정) 추적
- `payments`: 상태와 토스 키 대사

### 4-3. 정기 점검 (사람이 눈으로)
- **pending 상태로 오래 남은 결제 로그** - 불확정 건은 자동으로 해소되지 않을 수 있다
- 자동 환불 발생 건과 사유
- 사후 공개 검수 대기 건의 경과 시간 (유족이 기다리는 화면이다)
- 벤더 사용량·과금 (원가 추정치와 실측 대조)

## 5. 장애 대응 플레이북

### 5-1. 결제가 안 된다
1. 토스 상태 페이지 확인 (벤더 장애인가)
2. `payments` 최근 레코드 상태 분포 확인 - `ready`에 몰려 있으면 confirm 단계, `failed`면 승인 단계
3. 서버 로그에서 토스 응답 코드 확인
4. **불확정(타임아웃) 다발이면**: 사용자에게 "실패"로 안내되지 않는지 확인. 재시도를 유도하면 이중청구 위험
5. 필요 시 `PAYMENT_MOCK`은 **절대 켜지 않는다** (실결제를 가짜로 통과시킴)

### 5-2. 자동결제가 안 돌았다
1. 기동 로그에서 스케줄러 등록 확인
2. Redis 연결 상태
3. `subscription_payment_logs`에 당일 로그가 생성됐는가
4. 워커 프로세스 생존 확인
5. 수동 복구 시 **같은 날 중복 청구되지 않는지** 반드시 확인 (당일 로그 존재 여부부터)

### 5-3. AI 처리가 전부 실패한다
1. 벤더 API 키 유효성·잔액
2. S3 접근 권한
3. 워커 로그에서 실패 지점(다운로드/생성/업로드/DB 저장)
4. 자동 환불이 정상 동작하는지 - 안 되면 수동 환불 + 사과 통지

### 5-4. 사후 전달 사고 (최고 심각도)
잘못된 수신인에게 전달됐거나, 전달돼선 안 될 건이 나간 경우.
1. **즉시 해당 토큰 무효화**
2. `audit_logs`로 누가 언제 승인했는지 확인
3. 수신인에게 연락해 상황 설명 (자동화하지 말 것)
4. 유족에게 사실대로 알리고 대응 협의
5. 원인 규명 전까지 사후 공개 승인 일시 중단
- 이 유형은 기술 문제가 아니라 신뢰 문제다. 은폐 시도 금지.

### 5-5. 개인정보·민감데이터 유출 의심
음성·영상·사망증명서는 KMS 암호화 대상이다.
1. 접근 로그 확보 (`audit_logs`)
2. 영향 범위 산정
3. 법적 신고 의무 확인 (법률 검토 항목)
4. 키 로테이션
5. 이용자 통지

## 6. 백업·복구

| 대상 | 필요 |
|---|---|
| MySQL | 정기 자동 백업 + 마이그레이션 전 수동 백업. 복구 절차를 **실제로 한 번 리허설**해야 한다 |
| S3 (음성·영상·사진) | 버저닝 또는 별도 백업. **사용자의 유일한 원본일 수 있다** - 유실 시 복구 불가 |
| KMS 키 | 삭제 방지 설정. 키를 잃으면 암호화된 모든 데이터가 영구 복호화 불가 |
| Redis | 큐 상태. 유실 시 진행 중 작업이 사라지므로 재처리 절차 필요 |

**보관 기간**은 SPEC-05·SPEC-07의 데이터 정책과 법률 검토 결과를 따른다. 특히 "서비스 종료 시 데이터 반출 제공"을 약관에 명시하기로 했으므로, 그 절차도 실행 가능해야 한다.

## 7. 지금 결정·구축되지 않은 것

착수 전에 정해야 할 항목이다.

1. **실제 배포 환경 확정** - EC2인지 다른 것인지, 서버 사양, 워커 분리 실행 방식
2. **알림톡 벤더 선정** (SPEC-04) - 미착수
3. **모니터링 도구 선정** - 위 4절을 어디서 볼 것인가
4. **CI/CD 파이프라인 구성** - GitHub Actions 계획만 있음
5. **도메인·SSL** - `ondam.kr`이 PRD에 언급되나 확보 여부 [미확인]
6. **CS 채널** - 랜딩에 전화번호를 노출하기로 했는데 응대 주체·시간·도구가 미정
7. **백업 복구 리허설** - 한 번도 해보지 않았다
