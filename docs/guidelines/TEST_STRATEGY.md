# 온담 테스트 전략

> 작성 배경: Phase 0 결함 개선을 3라운드에 걸쳐 진행하는 동안 **실행 검증을 한 번도 하지 못했다.** 정적 리뷰만으로 3차까지 갔고, 매 라운드 새 결함이 나왔다.
> 그 원인은 리뷰어의 역량이 아니라 **검증 수단의 부재**였다. 이 문서는 그 공백을 메운다.
> 전역 규칙(`.claude/rules/testing.md`)의 온담 적용판이다. 커버리지 수치를 개발 중 상시 강제하지 않는다는 원칙은 그대로 유지한다.

## 1. 이 프로젝트에서 테스트가 특히 중요한 이유

1. **돈이 오간다**: 결제·정기결제·환불. 이번 감사에서 이중청구 경로가 두 번 발견됐고, 둘 다 "정상 경로"가 아니라 **네트워크 실패·크래시 같은 예외 경로**에 있었다. 예외 경로는 눈으로 읽어서 찾기 가장 어렵다.
2. **되돌릴 수 없는 전달이 있다**: 사후 영상 전달은 잘못 보내면 회수가 불가능하다.
3. **타겟이 5060이다**: 오류 화면 하나가 곧 CS 전화이고 이탈이다. 실패 경로의 UX가 성공 경로만큼 중요하다.
4. **mock이 실패를 가렸던 전력이 있다**: 화면이 정상으로 보이는 것과 실제로 동작하는 것이 다를 수 있다는 걸 이미 겪었다.

## 2. 레벨별 역할 분담

| 레벨 | 무엇을 잡는가 | 어디에 쓰는가 | 비중 |
|---|---|---|---|
| **정적 검사** | ENUM drift, 필드명 불일치, NOT NULL 누락, mock 잔존 | 병합 전 자동(G8 체크리스트) | 상시 |
| **단위 테스트** | 순수 로직: 금액 계산, 상태 전이 판정, 토큰 검증, 접미사 생성 | 로직이 조건 분기를 가질 때 | 선택적 |
| **통합 테스트** | DB·큐가 낀 흐름: 트랜잭션 롤백, 멱등성, 락, 워커 파이프라인 | **결제·구독·전달은 필수** | 핵심 |
| **E2E(Playwright)** | 사용자가 실제로 겪는 전 구간 + 실패 경로의 화면 | 최종 손테스트 직전 | 핵심 |
| **수동 실환경 검증** | 외부 벤더 실제 응답(토스·D-ID·알림톡) | 벤더 연동 변경 시 | 필수 |

**원칙: 이번 감사에서 드러난 결함 유형에 맞춰 투자한다.** 발견된 결함의 대부분은 (a) 코드↔스키마 불일치 (b) 예외·경계 경로 (c) 프론트/백엔드 계약 불일치였다. 순수 함수 단위 테스트로는 하나도 못 잡았을 것들이다. 따라서 **정적 검사 + 통합 + E2E에 무게를 둔다.**

## 3. 정적 검사 (자동화 1순위)

병합 전 스크립트로 돌린다. 이번 감사 결함의 상당수가 자동 검출 가능했다.

| 검사 | 방법 | 근거 |
|---|---|---|
| ENUM 4축 정합 | `enums.js` ↔ `ondam_schema.sql` ↔ Zod ↔ Repository 리터럴 대조 | 가입·주문·펫초상화가 전부 이것 때문에 죽어 있었음 |
| 프론트/백엔드 응답 필드 대조 | 프론트가 읽는 필드명 ↔ 백엔드 응답 shape | `orderId` vs `tossOrderId`로 결제 100% 실패, 갤러리 `url` vs `file_url`로 사진 0장 |
| mock 폴백 스캔 | catch 블록 내 성공 전환 패턴 | 40곳이 실패를 은폐했음 |
| NOT NULL 충족 | INSERT 컬럼 목록 ↔ 스키마 NOT NULL 대조 | `photo_files.file_size` 누락으로 사진 처리 완료가 항상 실패 |
| soft delete 필터 | `deleted_at` 테이블 SELECT/UPDATE에 필터 존재 | 삭제된 유언장을 관리자가 공개 처리 가능했음 |
| 환경변수 일관성 | 코드에서 참조하는 env ↔ `.env.example` ↔ `validateEnv` | `AWS_BUCKET_NAME` 오타로 모든 업로드가 `bucket: undefined` |

## 4. 통합 테스트: 반드시 자동화할 시나리오

DB(테스트 스키마) + Redis가 있는 환경에서 돌린다. 토스 등 외부 벤더는 스텁으로 대체하되, **스텁이 실제 응답 형태와 같은지는 수동 검증으로 별도 확인**한다(6절).

### 4-1. 결제 (최우선)
- 정상: prepare → confirm → `payments.status='done'`, target이 `paid`로 전이
- **금액 위조**: 클라이언트가 다른 금액을 보내도 서버 조회값으로 처리되는가
- **타인 리소스**: 남의 `targetId`로 prepare 시 403
- **이미 결제된 주문**: 재 prepare 시 차단
- **중복 confirm**: 동시 2건 → 토스 호출 1회, 나머지는 멱등 응답
- **타임아웃(불확정)**: 토스 응답 유실 시 `failed`로 확정되지 않고 선점이 유지되는가 → 재시도가 자가치유 경로를 타는가
- **명확한 실패**: 토스 4xx → `failed` 확정 + 재시도 가능
- **환불**: 취소 시 주문 상태가 `refunded`로 환원

### 4-2. 정기결제 (최우선)
- 스케줄러가 실제로 등록되고 발화하는가
- **응답 유실 후 재시도가 두 번 청구하지 않는가** (pending 유지 → 동일 orderId 재사용)
- 더블클릭·크론과 수동 재시도 동시 발생 → 결제 1건
- 실패 3회 → `past_due` → `suspended` 전이, 재시도 성공 시 `active` 복원 + `fail_count` 리셋
- 트랜잭션: 결제 성공 후 DB 일부 실패 시 전체 롤백 + 보상 환불

### 4-3. 회원·인증
- 가입 → 탈퇴 → **같은 이메일로 재가입** (UNIQUE 충돌 없이)
- 카카오 계정 탈퇴 후 재로그인
- 필수 동의 저장 실패 시 계정도 롤백 / 선택 동의 실패는 가입 성공
- refresh 토큰 회전, 동시 refresh 시 정상 사용자가 로그아웃되지 않는가

### 4-4. AI 파이프라인
- 사진 주문: 업로드 → 큐 → 워커 → 결과 저장 → 알림 (무개입 완주)
- 워커 실패 → 재시도 소진 → 자동 환불 + 통지 + 로그 3종
- 부분 실패: 성공분 제공 + 전액 환불
- 큐 페이로드 계약: 프로듀서가 넣는 필드 ↔ 워커가 읽는 필드

### 4-5. 사후 전달 (되돌릴 수 없으므로 엄격히)
- 유가족 요청 → 관리자 승인 → 수신인별 링크 발송 → 열람 → 다운로드
- 반려 → 재요청
- 토큰 만료 → 연장 → 구토큰 무효
- 승인되지 않은 상태에서 열람 시도 차단
- **오전달 방지**: 수신인이 아닌 사람의 토큰으로 접근 불가

### 4-6. 접근 제어
- 추모관: 코드 없으면 비공개, 코드 오답 차단, 정답이면 열람
- 관리자 role별 권한 매트릭스 (화면 숨김이 아니라 **API 레벨** 차단)
- 각 도메인 IDOR: 타인 리소스 조회·수정 불가

## 5. E2E (Playwright): 사용자 여정 기준

최종 손테스트 직전에 돌린다. **실패 경로도 함께 본다** - 5060 타겟에서는 실패 화면이 곧 CS다.

### 필수 시나리오
1. **자녀 선물 여정**: 자녀 결제 → 링크 전송 → 부모 무계정 수행(사진·녹음) → 완료 알림 (SPEC-01)
2. **사진관 단독**: 업로드 → 프리체크 → 결제 → 처리 대기 → 결과 수령 → 공유
3. **영상 편지 제작**: 동의(낭독 녹음) → 사진 → 수신인 → 결제 → 제작 완료
4. **유가족 열람**: 링크 진입 → 본인 확인 → "마음의 준비" → 재생 → 다운로드
5. **비로그인 공개 페이지**: `/watch/:token`, `/memorial/:slug`가 로그인 없이 열리는가 (이번에 튕기는 버그가 있었음)
6. **세션 유지**: 로그인 후 새로고침해도 유지, 로그아웃 후 보호 라우트 접근 차단

### 실패 경로 시나리오 (동등하게 중요)
- 결제 실패 → 사용자가 이해할 수 있는 한국어 안내 + 재시도 경로
- AI 처리 실패 → 자동 환불 안내
- 잘못된 접근 코드 → 명확한 안내
- 네트워크 오류 → **가짜 성공이 아니라 에러가 보이는가** (mock 폴백 재발 감시)

### 접근성·UX 검증
- 주요 CTA 버튼 48px+, 본문 16px+ 자동 측정
- 에러 메시지에 기술 용어·영문 원문이 노출되지 않는가
- 로딩 상태가 영구 스피너로 갇히지 않는가

## 6. 수동 실환경 검증 (자동화 불가, 벤더 연동 시 필수)

스텁으로는 절대 확인할 수 없는 것들. **벤더 연동을 바꿀 때마다 1회씩 실제로 확인**한다.

- **토스**: 동일 orderId 재전송 시 실제 거부 여부와 에러 코드(현재 멱등 설계 전체가 이 가정 위에 있음), 결제 조회 API 응답 형태, confirm 중복 호출 코드, 웹훅 서명 헤더 포맷
- **D-ID**: 한국어 오디오 립싱크 품질, 처리 시간, 실제 과금, Basic 인증 동작
- **ElevenLabs**: 음성 클론 품질, 원가
- **알림톡**: 템플릿 심사 통과, 실제 수신, SMS 폴백 동작
- 각 결과는 `docs/strategy/08-lipsync-vendor-comparison.md` 같은 실측 문서에 기록해 추정치를 실측치로 대체한다

## 7. 언제 무엇을 돌리나

| 시점 | 실행 |
|---|---|
| 코드 작성 직후 | 정적 검사 + 해당 영역 단위 테스트 |
| 병합 전 | 정적 검사 전체 + 관련 통합 테스트 + 빌드 |
| 결제·전달·인증 변경 시 | 해당 통합 시나리오 **전량** (부분 실행 금지 - 이번 감사에서 경계 결함이 반복됐다) |
| 벤더 연동 변경 시 | 6절 수동 검증 |
| 배포 전 | E2E 필수 시나리오 + 실패 경로 |
| 최종 손테스트 직전 | E2E 전량 (전역 규칙) |

## 8. 커버리지 정책

- 개발 중 상시 강제 수치는 두지 않는다(전역 규칙 유지).
- 다만 **결제·구독·사후 전달 3개 도메인은 예외**로, 위 4절 시나리오가 전부 통과하는 것을 병합 조건으로 한다. 수치가 아니라 **시나리오 목록 충족**으로 관리한다.
- 80% 커버리지는 "테스트 맡길게" 시점의 인수 게이트에만 적용한다.

## 9. 지금 없는 것 (구축 순서)

현재 프로젝트에 테스트 인프라가 사실상 없다. 아래 순서로 만든다.

1. **테스트 DB·Redis 기동 스크립트** (docker-compose 등) - 이게 없어서 이번에 아무것도 검증하지 못했다. 최우선
2. **정적 검사 스크립트** (3절) - 투자 대비 효과가 가장 큼
3. **결제·정기결제 통합 테스트** (4-1, 4-2) - 자금 직결
4. **E2E 필수 시나리오** (5절) - 배포 게이트
5. 나머지 통합 시나리오 확대
