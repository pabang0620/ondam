## 1. 이번 라운드에서 달라진 전제

## 2. 가장 무거운 발견: 동의 체계가 검증되지 않고 있었다 (출시 차단급)

경위상으로는 3-1(정적)과 3-2(실행)에 걸쳐 있으나, 단일 결함으로 이번 라운드에서 가장
무겁기 때문에 따로 적는다.

### 무엇이 문제였나

`user_consents` 테이블에 동의는 **저장되고 있었다.** 그런데 서버가 그 값을 읽고 처리를
막는 코드가 **음성권(voice) 한 종류를 빼고 0건**이었다. 초상권(portrait),
AI생성물(ai_generation), 사후공개(posthumous_release)는 화면에서 동의를 받아 DB에
넣기만 하고, 그 뒤 어떤 경로에서도 조회되지 않았다.

즉 동의 화면은 **기능이 아니라 장식**이었다. 스키마와 화면만 보면 정상으로 보이고,
"동의 컬럼이 있다"는 사실이 오히려 구현됐다는 착각을 만들었다.

### 실증된 우회

추정이 아니라 실제 요청으로 통과를 확인했다.

- 초상권 **미동의 상태에서 영정사진 주문** → `200`
- 초상권 **미동의 상태에서 AI 처리 큐 등록** → `200`
- DB에 **초상권 동의 0건인 사용자의 영상이 실제로 생성돼 있었다** (기존 데이터)

마지막 항목이 특히 중요하다. 가설이 아니라 이미 발생한 사실이었다.

### 함께 드러난 것

- **회원가입이 `terms`를 검사하지 않았다.** 화면은 필수 체크박스를 요구하지만 서버는
  `privacy`만 봤다. API를 직접 호출하면 약관 미동의로 가입이 된다. 약관 동의가 계약
  편입의 근거인데 서버가 강제하지 않고 있었다(`phase0-followups.md` B-5가 지적한
  "선택 처리"의 서버측 짝).
- **선물 수행 경로에 동의 4종이 통째로 누락**(`terms`/`portrait`/`ai_generation`/
  `posthumous_release`). 선물은 결제자와 수행자가 분리되는 구조라 수행자에게서 동의를
  받아야 하는데 화면 자체가 없었다.
- **AI 사진관은 전 경로에 초상권 동의 화면이 없었다.**
- **동의 저장 실패를 프론트·백엔드 양쪽이 조용히 삼켰다.** 저장이 실패해도 사용자에게는
  성공으로 보였다.

### 어떻게 고쳤나

1. **검증 게이트 신설** - photo/will/admin 서비스 계층에 동의 확인 추가. 미동의면 400.
2. **워커에서 재검증** - `photoWorker`/`videoWorker`가 실제 벤더를 호출하기 직전에 다시
   확인한다. **큐 대기 중 사용자가 철회하는 시나리오를 실제로 재현해 확인했다.**
   서비스 계층만 막으면 이 경로가 뚫린다.
3. **append-only 이력 전환** - `user_consents`의 `UNIQUE(user_id, consent_type)`를 제거.
   기존에는 `ON DUPLICATE KEY UPDATE`로 같은 행을 덮어써서 **철회·재동의 이력이 남지
   않았다.** 동의는 이력 자체가 법적 증빙이라 이 구조가 잘못이었다.
   부수 효과로 `voice_samples.consent_id`가 존재하지 않는 UUID를 가리키게 되는 FK 참조
   붕괴도 있었다.
   상세: `docs/migrations/2026-08-23-consent-history-and-evidence.README.md`
4. **증빙 보강** - `ip_address`·`user_agent` 기록. 저장 실패를 삼키던 처리 제거(필수
   동의는 저장 실패 시 요청 자체를 실패시킨다).
5. **동의 항목 SSOT 통합** - `frontend/src/components/consent/` 공용 컴포넌트로 모았다.
   경로마다 동의 목록을 따로 쓰던 것이 누락의 원인이었다.

### 지금 게이트가 걸려 있는 지점 (실측)

| 지점 | 확인하는 동의 |
|---|---|
| `willService.uploadVoiceSample` | voice |
| `willService.activateWill` | voice / portrait / ai_generation |
| `photoService.createOrder`, `photoService.startProcessing` (`assertPhotoConsents`) | portrait / ai_generation |
| `adminService.approveRelease` | posthumous_release (요청자가 아니라 `will.user_id` 기준) |
| `photoWorker` (벤더 호출 직전) | portrait / ai_generation |
| `videoWorker` (벤더 호출 직전) | voice / portrait / ai_generation |
| `giftPerformService.linkAccount` | privacy / terms (계정 단위) |

### 남는 것 (이번 라운드로 닫히지 않았다)

1. **철회 수단이 없다.** 동의는 이력으로 쌓이고 게이트도 작동하지만, 사용자가 자기 동의
   상태를 보고 철회하는 화면이 없다. 조회 API도 없다 - `POST /api/auth/consents`(저장)만
   있고 `GET`은 라우트 자체가 존재하지 않는다. 화면을 만들려면 조회 API 신설이 선행이다.
2. **`voiceWorker`에는 워커 단 재검증이 없다.** `photoWorker`·`videoWorker`와 달리
   `voiceWorker`는 ElevenLabs 음성 등록 API를 호출하면서 동의를 다시 보지 않는다.
   게이트는 상류 `willService.uploadVoiceSample`에만 있다. 즉 **큐 대기 중 철회 시나리오가
   음성 클론 경로에서는 여전히 열려 있다** - 이번에 videoWorker에서 재현해 막은 바로 그
   시나리오다.
3. **`pet` 도메인에 동의 검증이 0건이다.** 펫 도메인 전체에 consent 관련 코드가 없다.
   펫 AI 초상화도 AI 생성물이므로 `ai_generation` 동의 대상인지 판단이 필요하다
   (사람 초상권과 성격이 다를 수 있어 정책 판단이 선행이다).

위 3건은 후속 문서 E절에 등재했다.

> **주의할 만한 점**: 스키마 주석에는 원래부터 append-only가 설계 의도로 적혀 있었다.
> 즉 설계 문서가 맞았고 구현이 어긋난 것이었는데, 아무도 대조하지 않아 남아 있었다.
> 주석·문서가 구현을 보증하지 않는다.

## 3. 발견 경위별 분류 (이 문서의 핵심)

같은 결함이라도 어떤 방법을 써야 잡히는지가 다르다. 세 가지 방법이 **서로를 대체하지
못한다**는 것이 이번 라운드의 가장 실용적인 교훈이다.

### 3-1. 정적 분석으로 잡힌 것 (코드를 읽어서)

읽기만 해도 보이는 것들이다. 대체로 "쓰여 있어야 할 코드가 없다" 또는 "두 쪽의 계약이
다르다" 형태다.

| 발견 | 성격 |
|---|---|
| 동의 검증 코드가 0건 (초상권·AI생성물·사후공개) | 있어야 할 게 없음 |
| 회원가입이 `terms`를 검사하지 않음 | 있어야 할 게 없음 |
| 선물 수행 경로에 동의 4종 누락 | 있어야 할 게 없음 |
| `user_consents` UNIQUE + 덮어쓰기 vs 주석의 append-only 의도 | 설계-구현 불일치 |
| 죽은 연타 가드 (`useRef`가 아니라 렌더마다 새로 만들어지는 객체 리터럴) | 무효 코드 |
| `AbortController`를 만들고 `signal`을 요청에 넘기지 않음 (15개 파일) | 무효 코드 |
| 폐지된 구독 플랜 가격이 화면에 하드코딩돼 남아 있었음 (6절 참조) | 죽은 값 |
| 사용자 노출 명칭 "유언장" 잔존 (파생 표현 "유언 영상"·"유언 메시지" 포함) | 규칙 위반 |
| 벤더 SDK 원문·환경변수명이 사용자 응답에 노출 | 정보 노출 |
| `toss_payment_key`·`user_id`·`billing_kms_key_id` 응답 유출 | 정보 노출 |
| 관리자 화면에 영문 ENUM 원문 노출 | 표기 |

**공통점**: 실행해도 200이 나오고 화면도 뜬다. 무효 코드(연타 가드·AbortController)는
특히 그렇다 - **작동하지 않을 뿐 아무 증상이 없다.** 이런 것은 오직 읽어야 잡힌다.

### 3-2. 실행 검증(curl)으로만 잡힌 것

코드를 아무리 읽어도 안 나오고, 실제로 요청을 보내야 나오는 것들이다. 대부분
**드라이버·외부 시스템의 실제 동작**이 코드가 가정한 것과 달랐다.

| 발견 | 왜 읽어서는 안 나오는가 |
|---|---|
| **mysql2 prepared statement가 LIMIT/OFFSET 플레이스홀더를 지원하지 않아 목록 조회 8곳이 항상 500** | SQL도 코드도 문법상 정상이다. 드라이버 제약이라 실행해야 안다. **정기결제 크론의 `findDueSubscriptions`가 여기 포함돼 있었다 - 방치하면 자동결제 전면 정지** |
| BullMQ `getJobSchedulers()`가 식별자를 `key`로 반환하는데 `s.id`로 비교 → 스케줄러 3종이 항상 거짓 경보 | 라이브러리 반환 형태를 실측해야 안다 |
| `notificationWorker`가 서버·워커 두 프로세스에서 중복 기동 | 프로세스를 둘 다 띄워야 보인다 |
| 유가족 본인확인 5회 잠금이 **토큰 회전으로 완전 우회** | 잠금 키가 토큰 기준이라 새 토큰을 받으면 초기화된다. 실제로 6회 이상 시도해야 드러난다 |
| 유언 영상을 **결제 없이 활성화** 가능 (`draft` 허용) | 상태 전이를 실제로 밟아야 보인다 |
| **환불 경로가 한 번도 실행된 적이 없었다** - `PAYMENT_MOCK`이 환불 경로에 없어 환불 전량 실패 | 결제는 성공 경로만 밟혀 있었다 |
| 선물 만료 시 환불도 재발급도 막혀 결제금이 묶임 | 만료 상태를 실제로 만들어야 보인다 |
| 관리자 검수 화면의 요청자 정보가 항상 NULL (JOIN 대상이 `users`가 아니라 `will_beneficiaries`여야 했음) | JOIN은 문법상 정상. 결과가 비어야만 안다 |
| 펫 미디어 등록이 Zod `optional` ↔ DB `NOT NULL` 불일치로 500 | 양쪽 다 각각은 정상 |
| 같은 초에 두 번째 refresh가 동일 JWT를 만들어 UNIQUE 위반 | 초 단위 경합이라 연타해야 재현된다 (같은 초 20회 연속 성공으로 수정 확인) |
| 추모관이 존재하지 않는 슬러그(404)와 비공개 슬러그(403)를 다르게 응답해 존재 여부가 샘 | 두 요청의 응답을 비교해야 보인다 |
| KMS Encrypt API의 4KB 평문 제한으로 긴 영상 편지 텍스트가 저장 실패 | 외부 API 제한. 4096바이트 경계·한글 5000자·이모지 혼합으로 왕복 검증 |
| DATE 컬럼 UTC 드리프트 (`mysql2 dateStrings: ['DATE']`로 해소) | 드라이버 변환 동작 |

**한 문장 요약**: 정적 분석은 "우리 코드끼리의 약속"을 검사한다. **외부(드라이버·
라이브러리·벤더 API)와의 약속은 실행해야만 검사된다.**

### 3-3. 브라우저 렌더링으로만 잡힌 것 (여기가 제일 중요하다)

**이번 라운드 최악의 결함들이 전부 curl로는 200이었다.** API는 정상이고, 서버 로그도
깨끗하고, 스키마도 맞다. 그런데 사용자는 아무것도 못 한다.

| 발견 | curl 결과 | 사용자가 겪는 것 |
|---|---|---|
| **마이페이지 크래시** - 서버가 snake_case로 주는데 프론트가 camelCase로 읽음. `will_id`가 `undefined`인 채로 `.slice()` 호출 → TypeError | `200`, 정상 JSON | **화면이 흰 화면으로 죽는다** |
| **알림 설정 전 기능 불능** - 프론트가 쓰는 키 4개가 서버 응답에 없는 이름이라 GET은 항상 꺼짐으로 표시, PUT은 400, 그런데 catch가 조용히 원래 값으로 되돌림 | GET `200`, 응답 정상 | 켜도 안 켜진다. **에러 메시지조차 안 뜬다** |
| **토스 결제 4종 전부 무한 정지** (사진관·영상편지·선물하기·구독) - `getTossPayments`의 Promise가 `script.onload` 안의 동기 throw로 영구 pending | prepare API는 `200` | **결제 버튼을 눌러도 아무 일도 일어나지 않는다.** 에러도 없다 |
| **환불 후 처리 화면 무한 폴링** - `usePhotoProcessing`이 `refunded`를, `useWillProcessing`이 `failed`를 처리하지 않아 폴링 타이머가 멈추지 않음 | 상태 조회 `200`, 상태값 정확히 반환 | **스피너가 영원히 돈다.** 환불·실패 안내가 없다 |
| 펫 등록 후 `/pet/undefined`로 이동, 영상 편지 결제 `willId=undefined`, 구독 재결제·해지 `subscriptionId=undefined` | 등록 API `200`, id 정상 반환 | 다음 화면이 깨진다 |
| 관리자 주문·회원 목록 날짜가 `Invalid Date` | `200`, 날짜 정상 | 목록을 못 읽는다 |
| 서버가 준 실패 사유(`activateWill` 400 메시지 등)를 UI가 버리고 뭉뚱그린 문구만 표시 | `400`, **정확한 사유 포함** | 왜 안 되는지 알 수 없다 |
| 서버가 403으로 막는 권한 밖 admin 경로를 주소창으로 직접 열면 입력폼·등록 버튼이 그대로 렌더링 | `403` (정상 차단) | 화면상 권한이 있는 것처럼 보인다 |

**패턴이 하나다.** 백엔드는 옳고, 프론트가 그 응답을 잘못 읽거나 안 읽는다. 그리고
**그 사실이 서버 쪽 어디에도 기록되지 않는다.** 로그·상태코드·스키마를 아무리 봐도
안 나온다.

> **같은 결함이 브라우저로 밟지 않은 화면에 남아 있다.** 무한 폴링은 사진관·영상 편지
> 처리 화면에서 고쳤지만, 선물 수행 경로(`useGiftPerformPhoto`, `useGiftPerformWill`)의
> 폴링 루프는 이번에 브라우저로 밟지 않아 그대로다 - `useGiftPerformPhoto`는
> `completed`/`failed`만 보고 `refunded`에서 안 멈추며, `useGiftPerformWill.pollVideoReady`는
> 성공 조건만 있고 실패 분기가 아예 없다. 후속 문서 E절에 등재했다.
> **밟은 화면만 고쳐졌다는 것이 이 방법의 한계이자, 밟아야만 잡힌다는 증거다.**

> 응답 필드 표기가 도메인마다 다른 것(`snake_case` 그대로 vs 수동 camelCase 구성)이
> 위 목록 상당수의 근본 원인이다. `phase0-followups.md` C-1이 이미 지적한 문제인데,
> 이번에 그 대가를 실제로 치렀다. 통일은 파급이 커서 별도 스코프로 미뤘다(후속 문서).

### 3-4. 그래서 무엇을 해야 하는가

| 방법 | 잡히는 것 | 놓치는 것 |
|---|---|---|
| 정적 분석 | 없는 코드, 무효 코드, 계약 불일치, 정보 노출 | 외부 시스템의 실제 동작, 화면에서만 드러나는 것 |
| 실행 검증(curl) | 드라이버·라이브러리·상태전이·경합 | **프론트가 응답을 어떻게 쓰는지** |
| 브라우저 렌더링 | 화면 크래시, 무한 대기, 값 유실, 침묵 실패 | 부하·동시성·벤더 실동작 |

**완료 판정에 세 가지를 다 넣어야 한다.** 특히 "curl 200이니 됐다"는 이번 라운드에서
반복적으로 틀렸다. 이 교훈은 가이드라인 G13으로 규약화했다.

## 4. 병렬 작업의 경계

여러 에이전트가 backend/frontend를 나눠 동시에 작업했다. `G10`-4가 예고한 대로 **경계에서
결함이 생겼고**, 동시에 경계가 잘 지켜진 사례도 있었다. 둘 다 적는다.

### 4-1. 경계에서 나온 문제

- **필드명 drift 전반이 사실상 경계 문제다.** 백엔드가 응답 표기를 바꾸거나 유지하는
  동안 프론트가 다른 표기를 가정했다. 각자의 범위 안에서는 둘 다 정상이라 자기 쪽
  검증만으로는 절대 안 잡힌다(3-3의 대부분).
- **본인확인 상태코드**: 백엔드가 입력값 불일치를 `401`로 응답했고, 프론트 `apiClient`
  인터셉터는 `401`을 "토큰 만료"로 해석해 refresh 후 재시도했다. 그 결과 **1클릭에 시도
  횟수가 2회 차감**됐다. 어느 쪽도 단독으로는 버그가 아니다 - `401`의 의미에 대한 두
  범위의 해석이 달랐던 것이다. 백엔드를 `400`으로 정정하고(입력값 불일치는 인증 문제가
  아니다) 프론트는 무인증 공개 경로를 401 재시도 대상에서 제외하는 양쪽 수정으로 닫았다.
- **응답 필드 제거**: 추모관 접근 코드를 응답에서 빼는 보안 수정이 **프론트 3곳을
  깨뜨렸다.** 백엔드 범위 안에서는 올바른 수정이다. 이 사례로 가이드라인 G15를 만들었다.

### 4-2. 경계가 어긋나지 않은 사례

- **동의 값 정합성은 통과했다.** 프론트 공용 동의 컴포넌트가 보내는 `consent_type` 값,
  Zod 스키마, DB ENUM, 백엔드 조회 함수가 쓰는 값이 전부 일치했다. 동의 항목을 경로마다
  중복 정의하지 않고 **`frontend/src/components/consent/` 공용 컴포넌트 1곳으로 모아
  둔 것**이 이유다.
- 대조군이 명확하다. 같은 라운드에서 **SSOT를 둔 값(동의 유형)은 어긋나지 않았고,
  각자 쓰던 값(응답 필드 표기)은 대량으로 어긋났다.** 병렬 작업에서 경계를 지키는 방법은
  "조심하기"가 아니라 **공유 지점을 물리적으로 1곳으로 만드는 것**이다.

## 5. 수정이 회귀를 만든 사례

고친 것이 다른 것을 깨뜨린 경우다. 둘 다 **수정 자체는 옳았는데** 파급을 보지 않았다.

### 5-1. KMS 로컬 폴백이 에러 메시지 새니타이즈에 죽었다

- **원래 구조**: KMS 사용 불가 시 로컬 폴백으로 넘어갈지를 **에러 메시지 문자열을
  비교해서** 판단하고 있었다.
- **무엇을 고쳤나**: 벤더 SDK 원문·환경변수명이 사용자 응답에 노출되던 문제를 잡으려고
  에러 메시지를 안전한 문구로 정제(`toSafeFailureMessage`)했다.
- **무슨 일이 벌어졌나**: 정제된 메시지는 더 이상 원래 문자열과 일치하지 않는다.
  **분기가 조용히 죽어 폴백이 발동하지 않게 됐다.** 에러도 안 난다. 그냥 안 탄다.
- **어떻게 복구했나**: 문자열 비교를 버리고 **에러 코드 마커 + 화이트리스트 환경 검사**의
  이중 조건으로 재구성했다.
  - `utils/kms.js`가 예외에 구조적 마커를 붙인다: `{ status: 503, code: KMS_KEY_ID_MISSING_CODE }`.
    `wrapKmsError`는 `err.status`가 있으면 그대로 반환해 마커를 보존한다.
  - `willService.js`의 폴백 조건은
    `err.code === KMS_KEY_ID_MISSING_CODE && process.env.NODE_ENV === 'development'`.
  - 메시지가 어떻게 정제되든 `code`는 바뀌지 않으므로 같은 방식으로 다시 죽지 않는다.
  - 회귀 경위 자체는 `utils/kms.js` 주석에 남겼다. 다음 사람이 "왜 코드로 분기하는가"를
    묻지 않게 하기 위해서다.
- **교훈 2개**: (a) 에러 메시지 문자열로 분기하지 마라 → G12. (b) 폴백 조건은
  `!== 'production'`이 아니라 `=== 'development'`로 잠근다. 전자는 환경변수 미설정이나
  오타 시 **열린다** → G14.

### 5-2. AbortController 수정이 `onClick={refetch}`를 깨뜨렸다

- **무엇을 고쳤나**: `AbortController`를 만들고 `signal`을 실제 요청에 넘기지 않아 무효인
  코드가 15개 파일에 있었다. 훅의 조회 함수가 `signal`을 받아 요청에 전달하도록 고쳤다.
- **무슨 일이 벌어졌나**: 그 함수를 `onClick={refetch}` 형태로 버튼에 직접 물려 둔
  호출부가 있었다. React는 첫 인자로 **이벤트 객체**를 넘긴다. `signal` 자리에
  `MouseEvent`가 들어갔다.
- **교훈**: 함수 시그니처에 인자를 추가하면 **그 함수가 콜백으로 직접 전달된 곳이 전부
  호출부**가 된다. `onClick={fn}` / `onChange={fn}` / `.then(fn)` / `.map(fn)`은
  "인자를 안 주는 호출"이 아니라 "예상치 못한 인자를 주는 호출"이다.

> 두 사례 모두 **한 범위 안에서는 완결된 올바른 수정**이었다. 회귀는 범위 밖에서 났다.
> 이것이 G10-4(경계에 결함이 생긴다)의 또 다른 형태다.

## 6. 정합성·자금 관련 수정

3절의 경위 분류에 넣기 어렵지만 영향이 큰 것들이다.

- **AI 실패 시 상태 복원이 환불 여부를 안 봤다.** 최종 실패하면 무조건 한 상태로 두는
  바람에, **환불이 실패하면 결제금은 묶인 채 재시도도 막히는** 상태가 됐다.
  `payments.status`를 보고 환불됐으면 `draft`, 결제가 살아 있으면 `paid`로 복원하도록
  분기했다.
- **선물 환불 시 연결된 `wills`/`photo_orders`가 환원되지 않았다.** 결제는 환불됐는데
  콘텐츠는 살아 있어서 **결제 없이 사후공개까지 가는 경로**가 있었다.
- **폐지된 플랜 가격 하드코딩 제거 + 결제 금액의 정본을 서버로 통일.** 화면에 남아 있던
  폐지 플랜(구 `all` 9,900원 등) 항목을 걷어내고, 실제 청구 금액은 `preparePayment` 응답의
  `amountKrw`, 표시 금액은 서버가 응답에 싣는 `price_krw`를 쓰도록 했다.
  현재 서버 정본은 `subscriptionService.PLANS`의 `pet_archive` 4,900원 / 사진관 9,900원 /
  영상 편지 49,000원이다.
  **다만 화면 하드코딩이 전부 사라진 것은 아니다** - 랜딩·상품 소개 화면과
  `PetSubscriptionPage`(서버 플랜 목록을 받아 두고도 로컬 상수를 렌더한다)에 표시용 가격이
  남아 있다. 후속 문서 E절 참조.
- **5xx 메시지 안전화를 환경변수와 분리.** 이전에는 `NODE_ENV === 'development'` 문자열
  비교 하나에 의존해서, 배포 환경에서 설정 실수 한 번이면 내부 메시지가 전량 노출될 수
  있었다. 이제 `message` 필드는 `NODE_ENV`와 무관하게 항상 정제한다.
  단 `stack` 필드는 여전히 `NODE_ENV === 'development' && status === 500` 조건에 걸려 있다
  (잔여 위험은 `server.js` 주석에 명시). 4xx 메시지는 사용자에게 사유를 전달해야 하므로
  의도적으로 정제하지 않는다.
