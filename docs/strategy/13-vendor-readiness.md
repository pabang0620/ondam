# 13. 벤더 준비 상태표

> 작성 배경: 벤더 계정·계약·심사 준비 상태가 한 곳에 없어 **진짜 병목이 무엇인지 보이지 않는다.** OPERATIONS 1절에 `[미확인]` 표가 있으나 인프라 구성 요소 관점이고, "무엇을 신청해야 하고 얼마나 걸리는가"는 없다.
> 코드는 이미 대부분의 벤더를 호출할 준비가 되어 있다(`backend/.env.example` 39개 변수). 막힌 것은 코드가 아니라 **계정과 심사**다.
>
> **작성 원칙**: 심사 기간·요금을 확실하지 않으면 지어내지 않는다. `[확인 필요: 어디서 확인]`으로 남긴다. 실측 근거가 있는 것은 D-ID 요금뿐이다(08 문서, 2026-08-21 공식 페이지 크롤링).
> **현재 상태 열은 전부 `[미확인]`이다.** 실제로 확인한 사람이 이 문서를 갱신하면서 `[확인함 2026-MM-DD]`로 바꾼다.

## 1. AI 벤더

### D-ID (립싱크, 1차 확정 벤더)

| 항목 | 내용 |
|---|---|
| 용도 | 사진 + 음성 → 립싱크 영상 생성 (마지막 영상 편지의 핵심) |
| 필요 요건 | D-ID Studio 계정 + 유료 플랜 구독. 키는 Account Settings에서 **1회만 노출** |
| 인증 방식 | **Basic 인증** (`Authorization: Basic base64(USERNAME:PASSWORD)`). Bearer 아님 - 기존 어댑터 구현과 다를 가능성이 높은 핵심 교정점 |
| 심사·승인 | 없음 (카드 등록 후 즉시 사용 추정) |
| 월 최소 비용 | **Build $14.4/월** (오프라인 16분) ~ **Scale $138.6/월** (200분). Trial 14일·3분 무료 |
| 건당 원가 | 1분 영상 약 **$0.7~0.9** (Scale 플랜 기준, 15초 단위 반올림 과금) |
| 현재 상태 | `[미확인]` |
| 확인 방법 | D-ID Studio 로그인 → Account Settings에서 키 발급 여부·플랜 확인 |
| 없으면 막히는 것 | **영상 편지 전체.** Phase 3 진입 불가. DEV-01(립싱크 실검증)이 Phase 1 게이트이자 Phase 3 진입 조건 |
| 미확인 잔여 | 한국어 오디오 실동작·품질(문서 미명시, 실호출 스모크 필수) / 크레딧→초 정확한 환산 / 처리 시간 |

- Trial 3분으로 DEV-01 스모크 테스트가 가능하다. **유료 플랜 결제 전에 한국어 품질부터 확인한다.**
- `source_url`은 URL 방식만 지원하고 파일 업로드가 안 된다 → S3 presigned URL이 선행 조건이다(AWS 항목 참조).
- `result_url`은 D-ID S3 URI이고 만료가 있다 → 생성 즉시 온담 S3로 복사해야 한다.

## 2. 결제

### 토스페이먼츠

| 항목 | 내용 |
|---|---|
| 용도 | 단건 결제(사진관·영상 편지·선물) + 빌링 정기결제(펫 구독) |
| 필요 요건 | 상점 가입 + **심사 승인**. `[확인 필요: 가입 시 요구되는 서류·자격 요건 - 토스페이먼츠 가입 페이지 또는 영업 문의]` |
| 심사·승인 리드타임 | **있음.** `[확인 필요: 실제 소요 기간 - 토스페이먼츠 문의]` |
| 월 최소 비용 | `[확인 필요: 월 고정비 유무 및 결제 수수료율 - 토스페이먼츠 요금 안내]` |
| 필요 키 | `TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`, `TOSS_WEBHOOK_SECRET` |
| 현재 상태 | `[미확인]` |
| 확인 방법 | 토스페이먼츠 개발자센터 로그인 → 상점 상태·키 발급 여부 확인 |
| 없으면 막히는 것 | **판매 전체.** 결제가 없으면 어떤 상품도 팔 수 없다 |

- **이것이 가장 확실한 리드타임 병목이다.** AI 벤더는 카드만 있으면 당일 쓰지만 결제 심사는 기다려야 한다.
- 테스트 키로 개발은 가능하지만 DEV-25(결제 왕복 실구현)의 **실결제 검증**은 프로덕션 키가 있어야 한다.
- 웹훅 URL 등록에 **운영 도메인이 선행 조건**이다(도메인 항목 참조).
- 정기결제(빌링)는 단건 결제와 **별도 신청·심사일 수 있다**. `[확인 필요: 빌링 API 사용 신청이 별도인지]` 펫 구독(Phase 3) 시점 이전에 확인한다.

### 카카오 알림톡 (비즈니스 채널)

| 항목 | 내용 |
|---|---|
| 용도 | **1순위 알림 채널.** 결제·처리 완료·사후 전달 등 전 트랜잭션 통지 (SPEC-04) |
| 필요 요건 | ① 카카오톡 채널 개설 ② 비즈니스 채널 전환 ③ 발신프로필 등록 ④ **템플릿 개별 심사** |
| 심사·승인 리드타임 | **있고, 2단계다.** 발신프로필 승인 + 템플릿별 승인. `[확인 필요: 각 단계 소요 기간 - 카카오 비즈니스 또는 선정한 발송 대행사]` |
| 월 최소 비용 | `[확인 필요: 발송 대행사별 상이. 건당 단가 + 월 최소 사용료 유무]` |
| 현재 상태 | **벤더 미선정** (SPEC-04 4절, OPERATIONS 7절 2번). 미착수 |
| 확인 방법 | 카카오톡 채널 관리자센터 / 발송 대행사(알리고·솔라피·NHN Cloud 계열 등) 견적 문의 |
| 없으면 막히는 것 | **비동기 처리의 완결.** "다 되면 문자로 알려드릴게요"가 03 문서 3-2의 UX 전제이자 SPEC-08 3절의 수령 동선이다. SMS로 대체는 가능하나 비용이 오르고 도달 경험이 나빠진다 |

- **템플릿 심사가 진짜 병목이다.** 반려되면 문구를 고쳐 재제출해야 하고, 온담의 템플릿 중 상당수는 **죽음·사후 전달을 다루는 민감 문구**라 일반 커머스 템플릿보다 반려 가능성을 높게 잡아야 한다(SPEC-04 5절 문구 원칙).
- 대응: 변수부를 최대화하고 고정부를 무난하게 설계한다(SPEC-04 4절). 심사 반려를 전제로 **가장 민감한 템플릿(사후 공개 승인·열람 링크)을 가장 먼저 제출**한다.
- 벤더 선정 기준(SPEC-04 4절): 폴백 자동화, 템플릿 관리 API, 건당 단가.

## 4. SMS

| 항목 | 내용 |
|---|---|
| 용도 | 인증번호 발송(기구현) + 알림톡 실패 시 폴백 + 비회원(수신인·선물 수행자) 통지 |
| 현재 코드 | `.env.example`에 **Coolsms 키가 존재**(`COOLSMS_API_KEY`, `COOLSMS_API_SECRET`, `COOLSMS_SENDER`) → 인증 SMS는 Coolsms 전제로 구현된 것으로 보인다 |
| 필요 요건 | 발신번호 사전 등록(전기통신사업법상 의무). `[확인 필요: 발신번호 등록에 필요한 서류·소요 기간 - 해당 벤더 콘솔]` |
| 심사·승인 | 발신번호 등록 절차 있음 |
| 월 최소 비용 | `[확인 필요: 건당 단가 + 충전 방식 - 벤더 요금표]` |
| 현재 상태 | `[미확인]` (키 발급·발신번호 등록 여부 불명) |
| 확인 방법 | Coolsms 콘솔 로그인 → API 키·발신번호 등록 상태 |
| 없으면 막히는 것 | **회원가입 자체**(휴대폰 인증). 알림톡보다 먼저 필요하다 |

- **결정 필요**: 알림톡 벤더와 SMS 벤더를 하나로 통합할지, Coolsms(SMS) + 별도 알림톡 벤더로 갈지. SPEC-04는 "알림톡+SMS 폴백을 한 API로 처리하는 벤더"를 권한다. 통합하면 폴백이 자동이고, 분리하면 폴백을 직접 구현해야 한다.
- 통합으로 간다면 Coolsms를 대체하게 되므로 **인증 SMS 코드도 함께 바뀐다.** 벤더 선정을 미룰수록 재작업이 커진다.
- 발신번호 등록은 **CS 대표번호와 같은 번호를 쓸 수 있는지** 함께 확인한다(CS_PLAYBOOK 1-2).

## 5. AWS

| 항목 | 내용 |
|---|---|
| 용도 | S3(사진·음성·영상 저장) / KMS(민감 데이터 암호화) / EC2(앱·워커) / CloudFront(CDN) / Route 53(DNS) |
| 필요 요건 | AWS 계정 + 결제 수단 + IAM 사용자·정책 |
| 심사·승인 | 없음. 단 신규 계정은 일부 서비스에 사용 한도가 걸릴 수 있다 |
| 월 최소 비용 | 사용량 기반. **EC2 인스턴스 사양이 고정비를 결정한다.** `[확인 필요: 인스턴스 타입 결정 후 산정. OPERATIONS 7절 1번이 "실제 배포 환경 확정"을 미결정으로 남겨둠]` |
| 필요 키 | `AWS_REGION`(ap-northeast-2), `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `S3_BUCKET`, `KMS_KEY_ID` |
| 현재 상태 | 코드 연동 완료, **버킷·키·인스턴스 전부 `[미확인]`** (OPERATIONS 1절) |
| 확인 방법 | AWS 콘솔 → S3 버킷 목록 / KMS 키 목록 / EC2 인스턴스 / IAM 사용자 |
| 없으면 막히는 것 | **전부.** 파일 저장이 없으면 사진 한 장도 처리할 수 없다 |

세부 확인 항목:
- [ ] S3 버킷 생성 + 폴더 컨벤션(`photos/`, `wills/`, `pets/`, `profiles/`, `admin/`)
- [ ] **KMS 키 생성 + 삭제 방지 설정.** 키를 잃으면 암호화된 음성·영상·서류 전부 영구 복호화 불가
- [ ] IAM 정책 최소 권한 (S3 해당 버킷 + KMS 해당 키만)
- [ ] S3 버저닝 또는 별도 백업 (**사용자의 유일한 원본일 수 있다**)
- [ ] presigned URL 발급 가능 여부 (D-ID가 URL 입력만 받으므로 필수)
- [ ] Redis 호스팅 방식 결정 (EC2 자체 설치 / ElastiCache / 외부). `[확인 필요]`
- [ ] MySQL 8.4 호스팅 방식 결정 (RDS / EC2 자체 설치). `[확인 필요]`

## 6. 도메인·SSL

| 항목 | 내용 |
|---|---|
| 용도 | 서비스 주소. **토스 웹훅 URL·카카오 Redirect URI·알림톡 링크가 전부 여기에 의존** |
| 필요 요건 | 도메인 등록 + DNS(Route 53) + SSL 인증서(ACM 또는 Let's Encrypt) |
| 심사·승인 | 없음 (`.kr` 도메인 등록 요건은 `[확인 필요: 등록기관 안내]`) |
| 월 최소 비용 | 도메인 연 등록비 + Route 53 호스팅존 비용. `[확인 필요]` |
| 현재 상태 | **`ondam.kr`이 PRD에 언급되나 확보 여부 `[미확인]`** (OPERATIONS 7절 5번) |
| 확인 방법 | whois 조회 → 미등록이면 즉시 등록. 이미 타인 보유면 대안 도메인 결정 |
| 없으면 막히는 것 | **다른 벤더 등록이 전부 지연된다.** 웹훅·콜백·링크에 도메인이 들어가므로 선행 의존성이다 |

- **도메인이 선행 의존성이라는 점이 이 표의 핵심 발견이다.** 도메인 없이 토스 웹훅도, 카카오 콜백도, 알림톡 링크도 확정할 수 없다.
- `ondam.kr`이 이미 선점됐다면 **브랜드 표기까지 영향**을 받는다(11 문서). 가장 먼저 확인할 항목이다.

## 7. 이메일 (부가)

| 항목 | 내용 |
|---|---|
| 용도 | 영수증·약관 변경 등 기록성 통지 (SPEC-04: 주 채널로 쓰지 않음) |
| 현재 코드 | `.env.example`에 **Gmail OAuth2 전제**(`GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`, `GMAIL_USER`) |
| 필요 요건 | Google Cloud 프로젝트 + OAuth 클라이언트 + refresh token 발급 |
| 월 최소 비용 | 없음 (Gmail 발송 한도 내) |
| 현재 상태 | `[미확인]` |
| 확인 방법 | Google Cloud Console → OAuth 클라이언트 / 발급된 refresh token 유효성 |
| 없으면 막히는 것 | 영수증·기록성 통지. **출시를 막지는 않는다** |

- Gmail 발송은 일일 한도가 있고 도메인 발신이 아니라 스팸 분류 위험이 있다. 발송량이 늘면 전용 발송 서비스로 옮기는 것을 검토한다. 지금 결정할 일은 아니다.

## 8. 리드타임 기준 착수 순서

> 기준: **기다려야 하는 것부터.** 카드 등록으로 당일 해결되는 것은 뒤로 미룬다.
> 아래 순서는 확실한 리드타임 실측이 아니라 "심사 절차 유무"에 근거한 추정이다. 각 리드타임이 `[확인 필요]`인 만큼, **1단계 착수와 동시에 각 벤더에 소요 기간부터 문의**하고 이 문서를 갱신한다.

### 0단계: 도메인 (다른 모든 것의 선행 조건)
1. `ondam.kr` whois 확인 → 가용하면 즉시 등록, 아니면 대안 결정
2. Route 53 호스팅존 + SSL 인증서

**이유**: 토스 웹훅·카카오 Redirect URI·알림톡 링크가 전부 도메인을 요구한다. 여기가 막히면 1단계 신청서를 쓸 수 없다.

### 1단계: 심사가 있는 것 (병렬로 동시 신청)
3. **토스페이먼츠 상점 신청** - 판매 자체가 걸린 최장 리드타임 후보
4. **카카오 비즈니스 채널 전환 + 알림톡 발신프로필 등록**
5. **SMS 발신번호 등록** (알림톡 벤더와 통합할지 먼저 결정)
6. 카카오 로그인 앱 등록 + 동의항목 검수 신청

**이유**: 이 넷은 남이 승인해 줘야 끝난다. 내가 아무리 열심히 해도 단축되지 않는다. **가장 먼저, 동시에 넣는다.**

### 2단계: 심사 결과를 기다리는 동안
7. **AWS 계정·S3·KMS·IAM 구성** (당일 가능)
8. **Gemini API 키 + 유료 결제 계정** (당일 가능. 1차 출시 상품인 사진관의 유일한 AI 의존)
9. EC2·Redis·MySQL 호스팅 방식 확정 및 구축
10. **알림톡 템플릿 문안 작성·제출** - 발신프로필 승인 직후 바로 넣을 수 있게 문안을 미리 완성해 둔다. 민감 문구(사후 공개 승인·열람 링크)를 **가장 먼저** 제출해 반려·재제출 사이클을 앞당긴다

### 3단계: 영상 편지 준비 (Phase 3용, 1차 출시를 막지 않음)
11. **D-ID Trial(14일·3분)로 한국어 품질 스모크** - 유료 결제 전에 이것부터
12. ElevenLabs 계정 + 음성 클론 사용 요건 확인
13. 스모크 통과 후 D-ID 유료 플랜 결정 (Build $14.4 → 물량 늘면 Scale $138.6)

**이유**: 사진관 단독 출시(Phase 2)가 먼저다(05 문서). 립싱크 벤더 확정은 Phase 3 진입 조건이지 1차 출시 조건이 아니다. **단, D-ID 한국어 품질이 실패하면 상품 설계 자체가 흔들리므로 Trial 검증만은 앞당긴다.**

### 착수하지 않아도 되는 것
- 립싱크 예비 벤더(Sync.so·fal.ai) 계정 - 문서화만 유지(R5)
- 전용 이메일 발송 서비스 - Gmail OAuth로 충분

## 9. 병목 요약

| 순위 | 병목 | 왜 |
|---|---|---|
| 1 | **카카오 알림톡 템플릿 심사** | 심사가 2단계(발신프로필 + 템플릿별)이고, 온담 템플릿 상당수가 죽음·사후 전달을 다루는 민감 문구라 **반려·재제출 사이클을 전제해야 한다.** 남이 승인하는 데다 반복될 수 있는 유일한 항목 |
| 2 | **토스페이먼츠 상점 심사** | 승인 없이는 판매 자체가 불가. 리드타임이 단일 대기이므로 알림톡보다 예측 가능하지만 영향은 더 치명적 |
| 3 | **도메인 확보** | 리드타임은 짧지만 **1·2단계의 선행 조건**이라 여기서 막히면 전부 밀린다. 게다가 `ondam.kr`이 선점됐으면 브랜드 표기까지 영향 |
| 4 | **SMS 발신번호 등록** | 회원가입(휴대폰 인증)이 걸려 있는데 알림톡 벤더 선정과 얽혀 있어 결정이 미뤄지면 재작업이 커진다 |
| 5 | D-ID 한국어 품질 | 리드타임 병목은 아니지만(Trial 즉시 가능) **실패 시 상품 설계가 흔들리는** 유일한 항목. 확인은 빠를수록 좋다 |

**AI 벤더는 병목이 아니다.** D-ID·ElevenLabs·Gemini는 카드만 있으면 당일 쓴다. 병목은 전부 **심사가 있는 국내 서비스**(토스·카카오·SMS)와 그 선행 조건인 도메인이다. 08 문서가 "최대 병목은 립싱크 기술 검증"이라고 본 것은 기술 관점이고, 계정·계약 관점의 병목은 이쪽이다.
